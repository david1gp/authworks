# Team management

## Goal

Give organization administrators team management inside `/admin/users`:

- Teams have a name, a URL-safe slug, and exactly one team leader.
- People can be assigned to a team (and moved / unassigned) for better display, filtering, and management.
- A virtual **Unassigned** team contains every org member who is in no team.
- The admin user profile shows **who invited whom** (inviter of that user).
- Deliver screenshots of the integrated UI for review.

## Decisions (confirmed with user 2026-11-07)

1. **Scope: per organization, one team per person.** Assigning a person to a team moves them out of their previous
   team. Unassigned = org members (human users, not deleted, not service/machine users) with no team membership.
2. **Leader powers: manage own team only.** A leader sees/manages only their own team: add/remove members, view
   member profiles, invite people into the org + their team. Leaders cannot create/delete teams, change the leader,
   touch other teams, or org settings. Org owners/admins manage all teams.
3. **One leader, safe defaults.** Exactly one leader per team; the leader is a member of the team. Team name unique
   per organization. Deleting a team makes its members Unassigned (memberships removed, users/org memberships
   untouched). Profile shows inviter name/email, fallback `Unknown` / `System` when the inviter was purged
   (`invited_by = ""`) or is a system/bootstrap actor.
4. **Slug (added 2026-11-07).** Every team defines a URL-safe slug in addition to its name:
   - Pattern `^[a-z0-9]+(-[a-z0-9]+)*$` (lowercase alphanumeric, `-` the only special char, no leading/trailing or
     doubled hyphens), max length 64.
   - Unique per organization. `unassigned` is reserved for the virtual team and is rejected for real teams.
   - Slug is a required field on create/update public schemas. The UI auto-suggests it from the name (slugified)
     until the admin edits it manually, shows a URL preview, and validates live.
   - UI URLs address teams by slug (e.g. Teams tab state / team detail uses the slug, not the id). Changing a slug
     changes the URL; no redirects in v1.

## Approach

### New feature `src/features/teams/` (follows repo feature layout + code-style skill)

- Persistence (private Drizzle, DDL via `storageSchemaCreate.ts`):
  - `teams(id, realm_id, organization_id, name, slug, leader_user_id, created_at, updated_at, version)` —
    unique `(organization_id, slug)`, unique `(organization_id, name)`.
  - `team_memberships(id, realm_id, organization_id, team_id, user_id, created_at, updated_at, version)` —
    unique `(organization_id, user_id)` (enforces one team per person per org).
  - `leader_user_id` required at create and must be an org member; leader automatically holds a membership row.
  - Removing the leader's team membership → conflict; leadership is transferred first (leader change auto-adds the
    new leader as member, moving them from any previous team). A user who currently leads a team can never be
    moved/assigned to another team, named leader of another team, or used as leader at create — all return
    `teams.leader-conflict` (409) until leadership of their current team is transferred. This keeps the invariant
    "every team's leader is a member of that team, and one person leads at most one team".
- Public schemas (Valibot, one export per file, subject-first names, `Result` errors with unified error catalog
  codes like `teams.slug-conflict` 409, `teams.name-conflict` 409, `teams.not-found` 404):
  - Team view: `id, organizationId, name, slug, leader {userId, displayName?, email?}, memberCount, createdAt, updatedAt`.
  - Create/update inputs: `name`, `slug` (pattern above, `unassigned` rejected), `leaderUserId` (create; on update
    only admins may change it).
  - Teams list response includes `unassignedCount`.
- Actions + server routes (existing tenant pattern, guarded like organizations):
  - `GET/POST /realms/:realmId/organizations/:organizationId/teams`
  - `GET/PATCH/DELETE .../teams/:teamRef` where `teamRef` resolves by id first, then slug.
  - `POST .../teams/:teamRef/members {userId}` (assign/move), `DELETE .../teams/:teamRef/members/:userId` (unassign).
  - Authorization per action: org owner/admin (`organization.members.manage`) → all; team leader → read + member
    add/remove + rename/slug of **own team only**, no create/delete/leader-change; everyone else → denied.
    Org admins keep existing bypass semantics. Emit domain events following the existing events pattern
    (team created/updated/deleted, member assigned/unassigned, leader changed).
- Client (`teams/client/`) mirroring users/directory clients; library output entry if the repo pattern has one per
  feature; CLI commands only if trivially mirroring an existing feature CLI (otherwise skip and note it).

### Directory + organizations integration

- Directory org user list (`directoryUserListSchema.ts`) gains optional `team` filter accepting a team slug or
  `unassigned`; `directoryEntrySchema.ts` gains `team {id, name, slug} | null`. Filtering happens server-side.
- Invited-by: expose inviter on the organizations public invitation view as resolved
  `invitedBy {userId, displayName?, email?} | null`. For the admin user profile, directory user-access payload
  gains `invitedBy` for that user in that org — resolve from the accepted invitation matching org + user email
  (verify this join against the accept flow; if unreliable, use the membership-created event actor instead and say
  which was chosen). Handle `invited_by = ""` (purged) and system/bootstrap actors as `null` → UI fallback text.
- Leader invites: invitation create gains optional `teamId`; persisted nullable `team_id` on
  `organization_invitations`; on accept, a team membership is created. A leader may create invitations only with
  their own `teamId`; admins with any/none.

### Admin UI (directory feature UI, consuming teams via its client/public surface only)

- `/admin/users` tabs become `people | teams | service-accounts | invitations`. Tab + selected team + search live
  in URL params (existing pattern); selected team is addressed **by slug**.
- Teams tab: list of teams with name, slug, leader, member count; virtual **Unassigned** entry pinned (slug
  `unassigned`, computed count, no leader, not editable/deletable). Create/edit dialog: name, slug (auto-suggest
  from name until manually edited, live validation + URL preview), leader picker (org members). Delete confirms
  members become Unassigned.
- Team detail (within Teams tab, slug in URL): member list with leader highlighted, add-member picker (search org
  members, shows their current team; assigning moves them), remove member (→ Unassigned), change leader (admin
  only), edit name/slug. Unassigned detail lists unassigned people with assign controls.
- People tab: team filter dropdown (All / each team by slug / Unassigned) and a Team column (team name, muted
  "Unassigned" when none).
- User profile: Team field with assign/change/unassign control (visible to org admins; to a leader only for their
  own team scope — server enforces), and an **Invited by** row (name/email, fallback `Unknown`/`System`).
- Leader access: a plain org member who leads a team must be able to open `/admin/users` and see only their team
  scope. Extend route access + directory scoping accordingly (mirror `directoryUserAccess.ts`); do not silently
  drop this — if the contract system blocks it, stop and report.
- Demo fixtures: add teams + assignments + inviters to the directory/admin demo data so demo mode and screenshots
  show realistic content. All new strings via `messageTranslate` keys. Follow view-only `.tsx` + state-factory
  pattern used by the existing directory UI.

## Out of scope (v1)

- Sub-teams/hierarchy, multiple leaders, multiple teams per person, cross-org teams.
- Slug rename redirects, team avatars/colors, bulk assign, SCIM/LDAP team sync.
- Notifications to leaders on membership changes.
